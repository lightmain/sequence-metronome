- 自动测试只模拟音频输出；实体扬声器、蓝牙、系统延迟和人工听感仍未验收。

## 1. 结论

在“音频对齐”工作台的第一步之上增加一个左对齐的小按钮“设备延迟检测”，按钮上显示当前检测值。点击后，按钮展开为与第一步、第二步同宽的区域，在其中播放固定节拍并让用户打拍，统计出一个**打拍残留偏移**。该值只保存在浏览器 `localStorage`，不进入 TXT、JSON、曲目库、IndexedDB、撤销历史或未保存标记。第一步打拍换算首拍时自动扣除该值，从而减少设备输出路径和个人打拍习惯造成的系统偏差。

关键结论：

- 不新增“自动找首拍”功能。检测器只修正第一步打拍结果的系统偏移，不替代打拍，也不识别音乐节拍。
- 检测值不是硬件标称延迟。现有播放代码已经用 `getOutputTimestamp()` / `outputLatency` 估计可听时间；检测器测的是这个估计之后仍然残留的偏差，包含输出设备残余延迟和用户打拍偏早/偏晚的习惯。界面按用户要求仍叫“设备延迟”。
- 检测值只用于“打拍 → 首拍”的换算，写入对齐映射的 `start` 仍是与设备无关的音频时间。因此合成、导出、换设备播放都不需要再补偿该值，也不应把检测值写进曲目文件。
- 已保存的旧对齐不重算、不迁移。升级后只有重新对齐并使用检测值时才受影响。
- 没有检测值时行为与 V5 完全一致。

## 2. 调研：音游常见的延迟校准方案

### 2.1 方案对照

| 方案             | 代表做法                                                                             | 优点                                                                                 | 局限                                                                             | 本项目取舍                                  |
| ---------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------- |
| 跟随节拍打拍     | osu! Offset Wizard、StepMania 的机器/全局偏移校准、Cytus II 与 Arcaea 的 offset 设置 | 不需要额外硬件或权限；直接反映“玩家听到声音后再按键”的整条链路；可得到带符号的修正量 | 无法把设备延迟和人的打拍习惯分开；换设备或换人后需重测                           | **采用**                                    |
| 音画同步校准     | StepMania 的 video/global offset、部分 VR 音游和吉他游戏的校准                       | 能分别测量音频与画面延迟，适合判定依赖画面的游戏                                     | 本项目对齐只看声音，不需要画面偏移；实现和解释成本更高                           | 不采用                                      |
| 浏览器报告的延迟 | `AudioContext.outputLatency`、`baseLatency`、`getOutputTimestamp()`                  | 零操作、无需打拍                                                                     | 是估计值，蓝牙、驱动、系统混音和浏览器实现都可能未完全计入；不能反映个人打拍习惯 | 只作为现有播放的时间基准，不作为检测值      |
| 麦克风回环       | 扬声器播放、麦克风录制，互相关求声学往返                                             | 能测真实输出与输入链路                                                               | 需要麦克风权限和扬声器-麦克风摆放；易啸叫、受环境噪声影响；不适合网页节拍器      | 不采用                                      |
| 手动偏移滑杆     | 多数音游设置页的 offset 输入                                                         | 简单、可控                                                                           | 用户不知道填多少；容易反复试错                                                   | 仅保留第二步现有 ±1/±10 ms 微调，不新增滑杆 |

音游里的通行做法是“播放稳定的节拍，让用户跟着打，取多次打拍的中心趋势作为偏移”。[osu! Offset Wizard](https://osu.ppy.sh/wiki/en/Client/Options/Offset_Wizard)、[Project OutFox 的节拍器校准改进](https://projectoutfox.com/news/engine-chronicle-13-improving-metronome-calibration) 和 [Rhythm Quest 的延迟校准开发记录](https://ddrkirbyisq.itch.io/rhythm-quest/devlog/281351/devlog-10-latency-calibration) 都属于这一类；社区也常按设备收集 offset 参考值，例如 [Arcaea Device Offsets](https://arcaea.fandom.com/wiki/Device_Offsets)。这些做法通常只取平均/中位数或少量样本，本计划在此基础上沿用本项目第一步已有的统计口径，增加离群剔除和置信区间。

### 2.2 为什么不直接使用 `outputLatency`

- `outputLatency` 是浏览器对当前输出路径的估计，不是设备说明书上的延迟；不同浏览器、Windows 音频栈、蓝牙编解码和驱动会给出不同结果。
- `getOutputTimestamp()` 提供 `contextTime` 与 `performanceTime` 的对应关系，现有 `MusicPlayer.audibleTime()` 已用它估计“此刻真正听到的音频位置”，比单看 `outputLatency` 更接近实际。
- 这个估计仍可能有残差，尤其是蓝牙和浏览器后台/设备切换时。[MDN 的 `outputLatency` 说明](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/outputLatency)、[`getOutputTimestamp()` 说明](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/getOutputTimestamp) 以及 [Web Audio 规范讨论 #2461](https://github.com/WebAudio/web-audio-api/issues/2461) 都说明这些值是实现相关的估计，不能当作精确硬件延迟。
- 因此检测器比较的是“打拍时间”与“应用内估计的可听时间”，得到的是**还需要修正的残差**。这也正是第一步打拍实际需要的修正量。

### 2.3 人的打拍偏差

人跟着节拍器打拍通常会略微提前，文献中称为 negative mean asynchrony / negative synchronization error，常见量级是几十毫秒（参见 [Müller 等的讨论](https://www.sciencedirect.com/science/article/abs/pii/S0166411599800247)）。这意味着：

- 即使设备零延迟，检测值也可能不是 0，而是负值（打拍偏早）。
- 如果把检测值从第一步打拍结果中扣除，节拍器重拍会落在音乐的真实拍点上，而不是落在用户习惯性提前按下的位置。对“用节拍器提示拍点”的目标来说，这是期望行为。
- 但检测值不能解释为纯硬件延迟；换人、换输出设备、换打拍力度都可能改变它。界面文案按用户要求保留“设备延迟”，详细含义写入 README，不在界面增加说明段落。

## 3. 交互设计

### 3.1 收起态：第一步上方的小按钮

打开“音频对齐”后，工作台从上到下为：

```text
[设备延迟检测  +32 ms]              ← 左对齐的小按钮，宽度随内容
┌ 1  手动打拍 ────────────────────┐
│ ...                              │
└──────────────────────────────────┘
┌ 2  首拍位置与时间微调 ───────────┐
│ ...                              │
└──────────────────────────────────┘
```

- 按钮位于第一步之上，左对齐，不占满整行；与第一步之间沿用 `.workbench-steps` 的 14px 间距。
- 按钮文字为“设备延迟检测”，右侧显示当前值：
  - 未检测：`未检测`。
  - 已检测：带符号整数毫秒，例如 `+32 ms`、`−8 ms`、`0 ms`；正数表示打拍晚于应用内可听时间，负数表示偏早。
- 按钮为普通小按钮，不使用强调色；数值使用等宽数字（`font-variant-numeric: tabular-nums`）。
- `aria-expanded` 表示展开状态，`aria-controls` 指向展开区域。
- 第一步进行中可点击。第二步进行时按钮保留但禁用（见 3.5），因为检测值只影响第一步的打拍换算；要重新检测先点“返回上一步”。

### 3.2 展开态：与步骤同宽的区域

点击小按钮后，按钮消失，原位置出现一个与第一步、第二步同宽的 `section`：

```text
└──────────────────────────────────────────────────────────┘

│ ...（灰显、不可操作）                                    │

```

- 区域复用 `.workbench-step` 的边框、圆角、白底和内边距，宽度由 `.workbench-steps` 拉伸，与两步一致；标题行不带步骤序号，右侧是“收起”按钮。
- 展开时：
  - 立即停止对齐试听/打拍音频（`player.stop()`），避免两个声音源同时响。
  - 第一步和第二步加 `inert` 与 `.inactive`，保留视觉位置但不可操作。
  - 焦点移到“播放检测节拍”按钮。
- 收起时：
  - 停止检测节拍并丢弃本轮未“应用”的样本。
  - 恢复两步的可操作性，焦点回到小按钮。
  - 不自动恢复之前的播放。
- 展开区域内的 Esc 只收起检测区域，不关闭整个“音频对齐”对话框；再次 Esc 才关闭对话框。
- 不使用高度动画；直接切换，避免布局抖动和额外的 reduced-motion 处理。

### 3.4 键盘与焦点

- 检测运行中，Space 在播放按钮、打拍按钮或非按钮区域用于打拍；即使焦点在圆形播放按钮上，也拦截默认的按钮激活，避免同时触发暂停。焦点在“收起”“应用”“清除”等按钮时保留按钮自身的键盘行为。

- 中文输入法组合输入、文本输入框和滑杆保持现有行为；检测区没有文本输入。
- Esc 的优先级：检测区展开 → 收起检测区；否则沿用现有“取消本次对齐？”确认。

### 3.5 与两步流程的关系

- 检测器只在第一步可用。第二步时小按钮保留并显示已保存值，但禁用；用户点“返回上一步”后可重新检测。
- 检测值变化只影响之后的“下一步”换算。已经进入第二步后不会自动改动试听结果，避免把同一批打拍用两个不同延迟解释。
- 如果用户在第一步已经打了若干拍，再展开检测并应用新值，已记录的打拍保留为原始时间；点“下一步”时统一按新值换算。这样不需要清空打拍。
- 检测值不改变参考 BPM 的统计，也不改变第二步的 ±1/±10 ms 微调；用户仍可在第二步修正录音本身的拍点偏差。

### 3.6 样式与响应式

- 新增样式集中在 `src/style.css` 的对齐工作台段落，复用现有颜色变量和边框，不引入新色系、阴影或渐变。
- 小按钮：`align-self: flex-start`，`min-height` 约 30px，水平内边距约 10–12px，字号 13px，圆角与现有按钮一致。

- 在 `max-width: 900px` 和 `max-height: 780px` 的现有媒体查询中补充间距和字号，不新增断点。
- 展开后工作台总高度可能超过对话框，沿用 `.alignment-workspace .dialog-body` 的滚动，不在检测区内部再嵌套滚动。

## 4. 统计与计算

### 4.1 采样模型

检测节拍固定为 120 BPM（四分音符间隔 `interval = 0.5 s`），采用与应用内播放相同的音频时钟和可听时间估计：

- 按下“播放检测节拍”后，在 `AudioContext` 时间轴上安排一串等间隔点击音，首拍留出约 0.5 秒启动余量。
- 点击音的位置记为 `P_k = lead + k × interval`（相对于检测开始时刻），`k = 0, 1, 2, …`。
- 每次打拍记录事件时间 `E_i`（优先使用 `event.timeStamp`，不可用时退回 `performance.now()`），再用与应用内播放相同的 `audibleContextTime(context, E_i)` 得到“此刻可听位置” `A_i`。第一步打拍也改用事件时间，避免事件分发延迟被计入；这只是测量精度的改进，不改变打拍数据格式。
- 残差 `r_i = A_i − P_k`，其中 `k = round((A_i − lead) / interval)`，即把每次打拍归到最近的点击音。
- 只接受 `0 ≤ k < 最大节拍数` 且 `|r_i| ≤ 240 ms` 的样本；240 ms 约为半拍减 10 ms，明显落在两拍之间（例如打八分音符）的样本会被拒绝。单个样本最多可偏离 240 ms，但检测结果绝对值超过 200 ms 仍判为超范围。
- 同一个 `k` 出现多次时，只保留 `|r_i|` 最小的一个（双击/重复触发按更接近节拍的那次算）。
- 打拍顺序必须严格递增；暂停、停止或重新开始会结束本轮。

### 4.2 中心趋势与区间

对有效残差按从小到大排序：

1. 若样本数 `n ≥ 10`，从两端各去掉 `floor(0.1 × n)` 个极值，得到保留样本 `m` 个；`n < 10` 时不做截尾。
2. 检测值 `D = mean(保留样本)`，单位秒，最终按毫秒取整保存。
3. 样本标准差 `s = sqrt(Σ(r_i − D)² / (m − 1))`，均值标准误 `SE = s / sqrt(m)`。
4. 95% 置信区间 `D ± t(0.975, m − 1) × SE`；`t` 临界值复用第一步的 Student t 计算（把现有 `critical95` 提取为共享函数，不改变第一步结果）。
5. 同时计算保留样本的中位数作为交叉检查；中位数与均值相差超过 20 ms 时提示“打拍不稳定”，不直接应用。该检查只用于诊断，不改变展示的中心值。

采用截尾均值而不是简单平均，是为了减少一次明显误按对结果的影响；不直接采用中位数，是因为在样本量不大时中位数方差更大，且本项目已有均值/区间的统计口径。截尾后的标准差和区间是近似值，用于判断样本是否足够，不作为严格的推断结论。

### 4.3 判定门槛

| 条件         | 门槛                                            | 说明                                   |
| ------------ | ----------------------------------------------- | -------------------------------------- |
| 可计算       | 有效打拍 `n ≥ 8`                                | 少于 8 次不显示检测值，状态“样本不足”  |
| 推荐应用     | `n ≥ 16` 且 95% 区间半宽 ≤ 10 ms                | 状态“可用”，可直接应用                 |
| 精度不足     | `n ≥ 8` 但未达推荐条件                          | 状态“精度不足”；应用前弹出确认         |
| 结果异常     | 检测值绝对值 > 200 ms，或中位数与均值差 > 20 ms | 状态“结果异常”，禁止应用，提示重新检测 |
| 自动停止     | 有效打拍达到 24 或点击音达到 32 拍              | 先到者为准；用户也可手动停止           |
| 单次最大时长 | 约 16 秒（32 拍）                               | 超时自动停止，不无限播放               |

`n` 是归并、剔除后的有效打拍数；`m` 是 4.2 截尾后参与均值和区间计算的保留样本数。门槛按 `n` 判断，避免用户为了凑“截尾后 16 个”而多打两拍；区间仍按 `m` 计算。

门槛是初始值，实施后用真实设备实测再调整；不把 16 次、10 ms 写成通用统计标准。

### 4.4 如何应用到第一步

设：

- `L`：实际输出路径延迟；
- `L̂`：应用内 `audibleTime()` 对输出延迟的估计；
- `H`：用户相对听到的声音的打拍偏差（偏早为负）。

检测器测到

```text
D = L − L̂ + H
```

第一步打拍记录到的时间也包含同一项 `L − L̂ + H`。因此新的首拍为

```text
首拍 = 打拍回归/固定周期拟合得到的首拍 − D
```

实现上保持 `lockReferenceBpm()` 不变，在组件里对结果应用一个纯函数：

```ts
type AlignmentCore = { firstBeatMs: number; referenceBpm: number };

function applyDeviceDelay(core: AlignmentCore, delayMs: number): AlignmentCore {
  if (!Number.isFinite(delayMs) || Math.abs(delayMs) > 200) throw Error('设备延迟值无效。');
  return { ...core, firstBeatMs: core.firstBeatMs - delayMs };
}
```

- 只平移首拍，不改变参考 BPM、拍号或第二步的整拍移动。
- 没有保存值或值为 0 时，结果与 V5 完全一致。
- 检测值为负时，首拍向后移（`− (−8 ms) = +8 ms`），方向与“打拍偏早”一致。
- 对已有对齐重新对齐时，仍然从新的打拍结果计算；不会拿旧 `start` 再叠加检测值。
- 不修改已保存的 `start`。用户在第二步点“确定”后才写入新的 `start`，这个值已经包含检测修正，但它表示的是音频文件里的真实拍点，与设备无关。

### 4.5 为什么不在播放或合成时补偿

播放时，音乐和节拍器点击音经过同一个输出路径，相对同步不受设备延迟影响；需要修正的是“用户打拍记录的时间”与“音频文件真实拍点”的对应关系。把这个修正写进 `start` 后：

- 预览试听时点击音落在音乐拍点上；
- 导出的 WAV/MP3 在别的设备上仍然对齐；
- 换设备打开同一份对齐不需要重新补偿检测值。

因此检测值只影响“打拍 → 首拍”的换算，不影响播放调度、合成或导出。

## 5. 数据与存储

### 5.1 存储位置与格式

使用 `localStorage`，键名 `metronome.device.v1`：

```json
{
  "version": 1,
  "delayMs": 32,
  "taps": 18,
  "ci95Ms": [24, 40],
  "bpm": 120,
  "measuredAt": "2026-11-13T02:00:00.000Z"
}
```

- `delayMs` 是唯一参与换算的字段，整数毫秒，允许负数，有效范围 `−200…200`，与 4.3 的检测门槛一致；超出范围的值视为无效。
- `taps`、`ci95Ms`、`bpm`、`measuredAt` 只用于显示、诊断和以后排查，不参与计算；缺失或格式不对时忽略这些字段，不影响 `delayMs`。
- 读取时校验 `version === 1`、`delayMs` 是有限数；不合法则视为无值，不覆盖原始数据。
- 写入失败（隐私模式、配额、存储被禁用）时，本次对齐仍使用内存中的值，并通过现有消息对话框提示未保存成功。
- 清除时删除整个键。

### 5.2 不进入曲目数据

检测值明确不进入：

- `Song` / `Music` / `Alignment` 类型；
- TXT 的 `Alignment:{...}` 行；
- 曲目 JSON 的 `version: 3` 文档；
- `localStorage` 的 `metronome.workspace.v2` 曲目库文档；
- IndexedDB 的 `metronome.audio.v2`；
- 撤销/重做历史、`fingerprint()`、未保存星号、保存冲突检查；
- 合成音频和导出文件。

因此：

- 导出 TXT/JSON 再在另一台设备导入，不会带过去检测值；那台设备使用它自己的值或 0。
- Ctrl+S 不会保存检测值；刷新后检测值仍在，是因为它单独存在 `localStorage`，不是因为曲目库保存。
- 清除网站数据会同时删除检测值；换浏览器、换浏览器配置文件、换设备也不会共享。
- 旧版本网页不读取这个键，回退不会受影响；V6 也不要求升级曲目格式。

### 5.3 “与设备绑定”的实际含义

浏览器网页无法可靠识别当前输出设备：

- `navigator.mediaDevices.enumerateDevices()` 的 `audiooutput` 标签通常需要麦克风权限才可见，而且网页无法知道系统默认输出路由；
- `AudioContext.sinkId` / `setSinkId()` 是实验性能力，本项目没有输出设备选择界面；
- 同一个浏览器配置文件在同一网站来源下只有一个 `localStorage`。

所以 V6 的“设备绑定”实际是“本浏览器来源 + 本浏览器配置文件 + 当前输出路径 + 当前用户”。换耳机、换蓝牙音箱、换系统默认输出后应重新检测；换人使用同一浏览器也应重新检测。这个限制写入 README，不在界面增加提示。

未来如果需要真正按设备保存，需要先做输出设备选择和 `sinkId`，再按设备键存储；不在 V6 范围。

## 10. 风险与限制

- **语义混淆**：检测值是“打拍残留偏移”，包含个人打拍习惯，不是硬件延迟。界面叫“设备延迟”是用户指定的名称，README 必须解释清楚。
- **不可分离**：无法只测硬件延迟而不引入人的打拍偏差；更换打拍方式、设备或用户后应重测。
- **任务差异**：检测器跟随点击音打拍，第一步跟随音乐打拍；两者的人为偏差 `H` 不一定完全相同。检测值只能修正两者的共同系统偏移，不能保证每一步都完全贴合。人工验收要重点比较检测前后第二步所需的手动微调。
- **音量依赖**：检测节拍走现有主音量；如果用户把节拍器音量调到 0，检测区也会静音，而音量控制在模态对话框后面不可见。README 的验收步骤应提醒先确认音量，不新增检测区音量滑杆。
- **浏览器估计变化**：`getOutputTimestamp()` 的精度和实现相关，蓝牙、系统音频栈、后台切换都可能改变残差；检测值只代表测量时的情况。
- **设备切换**：网页无法可靠识别输出设备，换耳机/蓝牙后旧值可能失效；这是“与设备绑定”的实际边界。
- **数值风险**：错误应用会整体平移之后的打拍结果；用最低样本数、置信区间、异常值门槛和确认对话框降低风险。
- **存储边界**：隐私模式、存储配额、清除网站数据都会让值丢失；丢失后只是回到无值行为，不影响曲目数据。
- **旧对齐**：V6 不自动重算旧对齐；用户需要重新对齐才能用上检测值。不要在不告知用户的情况下改旧 `start`。
- **测试边界**：自动测试只能模拟音频输出，不能验证实体扬声器、蓝牙或系统延迟；必须保留人工验收。
- **界面密度**：展开区增加工作台高度，小屏幕需要滚动；不引入嵌套滚动或遮挡第二步。

- 与设备绑定，只存在浏览器缓存，不写入 TXT/JSON。
- 入口在对齐工作台第一步上方，左对齐小按钮，标注当前延迟数值。
- 点开后扩大为与第一步、第二步同宽、位于第一步之上的区域，显示检测器 UI。
- **检测值语义**：采用可直接修正第一步的“有效偏移”（含个人打拍习惯），而不是浏览器报告的硬件延迟估计。其作用仅在第一步到第二步的换算中出现一次；第二步确认后的毫秒数就是播放、合成、保存和导出的最终值。
- **应用方式**：检测完成后不自动保存；用户点“应用”才写入并收起。精度不足时先确认，确认后仍可应用。
- **第二步可用性**：第二步时小按钮禁用，需先“返回上一步”再检测；检测值变化不追溯修改已进入第二步的草稿。
- **统计门槛**：120 BPM、8 次可计算、16 次且区间半宽 ≤ 10 ms 推荐、检测值绝对值 ≤ 200 ms、最多 32 拍、目标 24 次有效打拍。

### 实现采用的其他默认值

1. **显示范围**：显示检测值、95% 区间、有效打拍数和状态；不显示标准差、中位数等更多统计量，避免界面过密。
2. **清除**：不弹确认；清除只影响设备值，不影响任何曲目或已保存对齐。
3. **检测启动**：展开后不自动播放，必须点“播放检测节拍”，避免打开面板就突然发声。
4. **动画**：不做高度展开动画；直接切换。
5. **旧对齐**：不自动重算；仅重新对齐时生效。
6. **存储键名**：`metronome.device.v1`；整数毫秒；负值合法。
7. **状态显示**：标题右侧显示已保存值；本轮检测值单独显示在“延迟”读数中。
8. **单次残差**：单个打拍最多偏离最近节拍 240 ms；检测结果绝对值超过 200 ms 仍判为超范围。

### 后续可选增强

- 在检测值与浏览器 `outputLatency` 明显不符时提示“可能已更换设备”；当前不做自动判断，只在 README 说明。
- 检测器在没有关联音频时也可用；当前入口在“音频对齐”工作台内，必须有当前音频才能打开工作台。
- 按输出设备保存多个值；需要先做设备选择和 `sinkId`，不在 V6 范围。
- 把检测值作为“当前浏览器/用户”而非“设备”命名；界面按用户要求保留“设备延迟”。
